# 错误 1102：代码审计与本地性能分析

分析日期：2026-10-20。对象：当前本地项目；用户确认线上使用 Cloudflare Workers 免费套餐。

## 结论与证据边界

Cloudflare 官方错误表将 1102 定义为 Worker 超出 CPU 时间限制。免费套餐的 HTTP 请求 CPU 预算为 10 ms。项目存在多处计算开销偏大的实现，其中保存时的文本提取、UTF-8 截取，以及请求内的旧正文迁移是优先排查对象。

截图中的提示由 `src/api.ts` 的 `summarizeApiError` 从上游 HTML 错误页提取错误代码后生成。这证明请求收到了平台错误页，不是应用主动抛出的“1102”业务错误。普通网络不通走的是不同提示。

本次完成了源码审计、官方文档核对、原函数的本地测量。没有线上请求记录和 Workers CPU 日志，因此不能确认截图对应的具体路由、笔记大小、超限阶段，也不能把本地耗时当作 Cloudflare 实际 CPU 时间。以下明确区分可确认的实现缺陷与需要日志确认的触发条件。

官方资料：

- https://developers.cloudflare.com/workers/observability/errors/
- https://developers.cloudflare.com/workers/platform/limits/#cpu-time

CPU 时间是执行代码消耗的时间；等待 D1、R2、网络返回的时间不等于 CPU 时间。前端设置的 90 秒请求超时不会增加 Worker CPU 预算。免费套餐也不能只靠添加更大的 `limits.cpu_ms` 获得付费预算。偶尔允许的突发执行不应作为稳定性保证。

## 1. 保存路径承担了过多工作

前端 `saveDraft` 每次发送标题、图标、标题样式和完整正文，包括只修改标题的情况。850 ms 是编辑停止后的防抖时间，并非每 850 ms 固定发一次。

后端 `updateNote` 的完整正文更新依次涉及：

1. 查出当前笔记，再读取和解析旧正文。
2. 读取、解析新正文，递归处理嵌入媒体。
3. 序列化新正文并写入 R2 新对象。
4. 从正文提取摘要，更新 D1 中的正文对象指针。
5. 删除旧正文对象。
6. 再从正文提取搜索文本，更新搜索索引和附件引用表。
7. 扫描旧、新正文，检查并清理被移除的附件。
8. 序列化完整笔记并返回。

这些操作全部处在保存请求的成功响应之前。多次全量扫描、编码和对象分配共享该次请求的 CPU 预算；一处热点就可能耗尽免费预算。R2 写入本身的等待时长不能直接解释 1102，相关正文计算才是本次明确发现的问题。

## 2. 两个文本函数存在明确的重复计算

### collectSearchText

在每次递归调用入口执行：

```ts
if (byteLength(parts.join(" ")) >= NOTE_SEARCH_TEXT_MAX_BYTES) {
  return;
}
```

`byteLength` 每次都会创建 `TextEncoder`，完整编码当前字符串。每访问一个节点，都重新拼接、编码此前收集的文本；接近上限时，每次检查都接近重新处理 16 KB。

达到上限后，当前递归会返回，但外层循环仍继续调用后续节点，于是仍会反复拼接、编码同一份文本。该实现的开销不能用“最终索引只有 16 KB”来衡量。

### truncateUtf8

为了截取一个字符串，每添加一个字符都执行：

```ts
byteLength(result + char)
```

这会从头编码每个逐渐增长的前缀。截取阶段的累计处理量接近平方增长。约 16 KB 的中文搜索文本，其几千个前缀加起来能产生几十 MiB 的编码工作。

此外，摘要最终只保留 512 字节，却先使用同一套 16 KB 搜集逻辑；随后搜索索引再执行一次搜集。可将正文扫描与字节预算合并，一次生成摘要和搜索文本，在达到预算时停止遍历。

## 3. 本地测量

脚本 `diagnostics/profile-note-hotspots.mjs` 直接从 `src/worker.ts` 读取实际函数，剥离 TypeScript 类型后执行，没有改写被计时算法。样本为普通中文段落，每段包含四个富文本片段，不含图片。每项预热后采样七轮，取中位数。编码计数单独执行，不计入计时。

环境：Node v24.19.0。本地运行命令：

```powershell
node diagnostics/profile-note-hotspots.mjs
```

| 段落数 | 正文 JSON | 摘要处理，本地 ms | 搜索文本处理，本地 ms | 两步累计编码数据量 |
| --- | ---: | ---: | ---: | ---: |
| 20 | 12.8 KiB | 6.082 | 5.566 | 3.67 MiB |
| 100 | 64.2 KiB | 27.420 | 129.465 | 66.84 MiB |
| 300 | 193.0 KiB | 32.518 | 135.778 | 73.12 MiB |
| 1000 | 643.4 KiB | 64.125 | 169.310 | 95.10 MiB |

100 段落样本：摘要 1334 次编码，搜索文本 7308 次编码。约 64 KB 的正文处理产生约 67 MiB 累计编码工作，足以解释为什么免费 Worker 的 CPU 预算容易承压。这是累计处理量，不代表同时驻留内存达到该大小，也不能据此断言发生内存超限。

计时未包含鉴权、D1、R2、整个请求的 JSON 处理和全部保存步骤。完整结果保存在 `diagnostics/note-hotspots-results.json`。数据说明算法有明显浪费，具体线上超限阈值必须在 Workers 环境测量。

## 4. 刷新和加载为什么也受影响

`bootstrap` 依次请求 `/api/status`、`/api/notes`，再读取选中的笔记。列表失败时，尚未进入单篇正文加载，就可能失去整个工作区的初始化结果。

`listNotes` 在返回列表之前，同步迁移最多 8 篇尚未迁移的旧笔记。迁移包含 R2 写入、摘要提取、D1 更新、搜索与附件索引生成，复用了前述热点。

因此，如果账号还有旧正文，刷新页面本身就会触发重活。如果超限发生在迁移标记写入之前，下一次刷新仍可能选中同样的笔记；如果发生在标记写入之后，则可能留下已迁移正文但索引尚未完成的状态。实际是哪一种要看日志和数据库状态。

正常读取已经迁移的单篇笔记不会执行搜索文本提取，不能直接将所有 GET 失败都归因于该函数。它仍需要解析正文、扫描子页面链接，必要时重建正文树并序列化响应；超大正文等情况下也要单独测量。

另外，`bootstrap` 和 `loadNote` 依赖 `hasUsers`，启动时又通过 `setHasUsers` 修改该值。首次从 false 变成 true 会改变回调标识，使初始化 effect 再执行一轮，增加重复请求。这是放大因素，不等于无限循环或已确认的直接根因。

## 5. 前端如何放大用户体验问题

- **失败不会自动恢复。** 保存 catch 只设置错误状态；防抖 effect 不依赖保存错误状态。正文不再变化时，失败本身不会安排下一次尝试。手动保存、再次编辑等动作可能重新触发，但没有退避重试或联网恢复处理。
- **没有持久化正文草稿。** 当前笔记草稿和撤销历史存在 React 状态/ref 中；现有 localStorage 用于侧栏和分享密码等偏好。Service Worker 缓存应用资源，不缓存正文 API。刷新或关页后，尚未成功保存的修改没有可靠的本地恢复来源。
- **切换页面依赖保存成功。** `selectNote` 在 dirty 时先保存，返回 false 就直接退出。因此一次保存失败会阻止用户进入另一篇笔记。
- **临时服务故障表现得像需要重新登录。** 初始化中，即便不是 401，而是其他 API 错误，也会锁定工作区并显示登录界面；这会混淆服务异常和会话失效。
- **保存队列缺少版本合并。** 同一篇笔记同一 revision 会去重，但不同 revision 顺序入队，不会自动丢弃已经过时的未开始快照。请求慢时可能积压多份完整正文保存。
- **关页补发不可靠。** beforeunload/pagehide 会调用普通异步保存，浏览器可以取消这些请求。阻止离开提示有一定保护，但不能代替持久草稿。

## 6. “保存失败”不一定表示正文完全未写入

当前保存先写 R2，再更新 D1 指针，随后才维护搜索和附件引用。若平台在正文已提交后、响应返回前终止请求，客户端会收到失败，但正文可能已经保存；搜索或引用索引也可能只完成一部分。

反之，如果在提交之前被终止，本次正文就没有成为有效版本。截图无法区分这些状态。可靠方案需要提交版本标识、明确的提交边界，以及可恢复的索引维护。清理旧对象和附件还应考虑并发读取、索引延迟和失败重放，避免把恢复机会提前删除。

## 7. 建议处理顺序

1. **先保护编辑内容。** 按账号和笔记持久化本地草稿，明确“本地已保存 / 云端待同步 / 云端已同步”；建立刷新恢复流程。对短暂失败做有上限、带退避的重试，使用最新快照；409 冲突单独处理，避免盲目覆盖。
2. **消除 CPU 热点。** 维护累计字节数，避免每个节点重新 join/encode；用一次扫描完成 UTF-8 截取；摘要按 512 字节停止；合并摘要与搜索文本提取。普通媒体 URL 走快速路径，避免没有内嵌文件时也为所有字段创建异步任务。
3. **缩短保存的关键路径。** 标题、图标等修改只提交对应字段；正文保存合并过时版本。将正文指针、版本和必要引用一致性作为提交边界；垃圾清理可延迟执行，搜索可按要求异步维护。附件引用与垃圾清理的先后关系必须一起设计。
4. **让列表成为轻量读取。** 移除列表和正文读取中的同步迁移，改成受控的独立迁移任务或队列消息；分页迁移并允许恢复。仅使用 `waitUntil` 不会给同一次请求重新分配一份免费 CPU 预算。
5. **补齐生产证据。** 检查或开启 Workers observability，按路由统计 CPU、超限 outcome、正文大小、阶段和请求标识；前端记录 HTTP 状态、1102 与 CF-Ray，避免只留下通用提示。记录元数据即可，不需要记录笔记正文或密码。
6. **评估套餐。** 若需要快速缓解生产故障，Workers Paid 的默认 HTTP CPU 预算为 30 秒，可以显著放宽空间；它不能替代草稿保护和性能修复，也不能保证网络或存储故障消失。

## 8. 验收标准

- 在实际 Workers 环境分别测量保存、已迁移正文 GET、列表 GET，观察 CPU 分布和超限次数。
- 覆盖中文长文、多段富文本、图片引用、多级子页面和仍有旧正文的账号。
- 免费套餐验证应留出 CPU 余量；仅本地构建通过或本地计时改善不足以证明线上不再超限。
- 模拟保存失败、网络断开、关闭页面后重开，确认草稿能恢复，联网后能继续同步。
- 模拟“提交成功但响应失败”、并发修改和索引维护失败，验证版本、附件引用及重试行为。

## 9. 本次实现和验证（2026-10-20）

前面各节描述的是修改前的行为。本次已落实以下优化：

- 摘要与搜索文本提取改为累计 UTF-8 字节预算，到达上限立即停止遍历；摘要只读取所需的 512 字节。普通文本不再反复拼接并编码完整累积字符串。
- 普通正文绕过内嵌文件的异步重建，非文件 URL 绕过 URL 解析。
- 列表及正文 GET 不再同步迁移旧正文；旧正文仍可读取，实际编辑并保存正文时再写入新存储。没有把迁移简单搬到同一请求的 `waitUntil`。
- 标题、图标等编辑在正文未变时省略正文上传；保存队列丢弃尚未执行的过期版本。
- 按账号、笔记同步备份本地草稿，编辑后短暂防抖写入；离开页面时再次写入。刷新优先打开上次未同步的页面。浏览器存储配额或权限失败会明确提示，不能承诺所有大小的草稿都可备份。
- 对网络错误、408、429 和 5xx 最多自动重试三次，间隔为 1.5、4、10 秒；重新联网和手动操作可再次尝试。401、409 不自动重试。
- 保存请求携带已确认版本，服务端在修改前和数据库更新时检查版本。恢复草稿发现云端版本改变时停止自动保存，要求用户核对并选择版本；再次刷新仍保留冲突。旧保存响应不能删除更新的本地草稿。
- 初始化失败显示重新连接入口；修复标题编辑器首次挂载时可能没有显示已恢复标题的问题。
- 开启 Workers observability；API 记录开始、结束、错误、请求 ID 和脱敏路由。响应暴露 `X-Request-ID` 和 `CF-Ray`，前端失败日志保留 HTTP 状态及请求 ID。应用日志不输出正文、分享令牌、用户 ID 或密码。

验证记录：

- `pnpm check`：10 项 Node 回归测试、TypeScript 检查及 Vite 生产构建通过。测试覆盖 UTF-8 边界、提前停止遍历、旧正文只读、元数据保存、并发版本保护、附件引用顺序、本地草稿隔离和旧响应保护。
- `pnpm exec wrangler deploy --dry-run`：Worker 与静态资源成功打包，无实际上传。
- Playwright CLI 浏览器使用模拟 API，验证非首篇笔记的草稿恢复、503 后备份、三次自动重试后停止、编辑后刷新恢复最新内容、手动重试、仅标题 PATCH 不含正文、冲突跨刷新保持、主动使用云端版本及请求未返回时继续编辑不被旧响应覆盖。移动端 390px 宽度的冲突提示和选择按钮可正常操作。脚本为 `tests/browser-reliability.cjs`，需先运行本地 Vite。

本次没有重构正文提交后的搜索/附件索引为独立事务或队列。平台若在正文提交后终止执行，仍可能出现“客户端报失败但云端正文已更新”的状态；重载时若云端与本地内容相同，会清除已同步草稿，若不同则保留并提示核对。索引的事务化与恢复任务仍是后续工作。

部署后请在 Cloudflare 控制台选择对应 Worker 的 Observability / Logs，按保存 PATCH、列表 GET、正文 GET 分别检查 CPU 时间和超限 outcome。复现时记录时间、HTTP 状态、请求 ID 或 CF-Ray 即可，无需提供笔记正文或登录信息。日志里的 `elapsedMs` 是包含等待的墙钟耗时，**不是 CPU 时间**。1102 强制终止可能绕过 catch；只有 `api.begin` 没有 `api.end` 的请求需要结合平台 outcome 判断。
